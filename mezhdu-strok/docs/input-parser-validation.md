# МЕЖДУ СТРОК — INPUT / PARSER / VALIDATION FIX

## Цель

Исправить ситуацию, когда нормальный человеческий ввод приводит к ошибке:

> «Не получилось подтвердить достаточно связей».

Система должна:

- понимать свободный человеческий текст;
- не требовать специального синтаксиса;
- показывать лучший доступный результат;
- не требовать искусственного количества паттернов;
- позволять человеку после результата дополнить исходные данные и получить более богатый анализ.

---

# 1. Пользователь не обязан соблюдать формат

Пользователь может писать:

- через запятые;
- через точки;
- через `;`;
- каждый выбор с новой строки;
- обычными предложениями;
- несколько деталей внутри одного предложения;
- с опечатками;
- разговорным языком.

Все варианты должны работать.

Например, одинаково валидны:

> стейки, сидр, бег, сноуборд

и:

> Стейки. Сидр. Люблю бегать. Катаюсь на сноуборде.

и:

> Люблю путешествовать, особенно на машине или самолёте.

Не заставлять пользователя учить синтаксис продукта.

---

# 2. UX-текст возле поля

Показать:

**Пиши как удобно — списком или обычным текстом.**

Дополнительная маленькая подсказка:

**Можно через запятые, точки или с новой строки.**

Это подсказка, а не техническое требование.

---

# 3. УБРАТЬ regex как основной Parser

Нельзя использовать:

```js
split(/[,;\n]+/)
```

как способ определить пользовательские выборы.

Причина:

`путешествовать, на самолёте или машине`

является одним смысловым выбором, а не тремя.

А:

`стейки. сидр. бег.`

является тремя выборами, хотя здесь нет запятых.

---

# 4. Добавить отдельный PARSER перед Analyst

Pipeline:

```text
RAW USER TEXT
↓
PARSER
↓
STRUCTURED ITEMS
↓
ANALYST
↓
CRITIC
↓
WRITER
```

---

# 5. PARSER SYSTEM PROMPT

Ты получаешь свободный текст о вещах, занятиях, людях, местах и опытах, которые нравятся человеку.

Твоя задача — выделить смысловые единицы.

Не анализируй человека.

Не ищи связи.

Не интерпретируй причины, если пользователь их явно не указал.

Только структурируй ввод.

## Правила

### 1

Пунктуация — подсказка, а не строгая граница объекта.

Точка, перенос строки, запятая или союз могут разделять разные выборы.

### 2

Определяй границы по смыслу.

Например:

> путешествовать, на самолёте или машине

→ один смысловой объект:

`путешествовать на самолёте или машине`

Не:

- путешествовать;
- самолёт;
- машина.

### 3

Если явно перечислены независимые вещи:

> стейки, сидр, бег

→ три объекта.

### 4

Если пользователь написал несколько самостоятельных мыслей через точки:

> стейки. сидр. гулять по паркам.

→ три объекта.

### 5

Сохраняй формулировку пользователя максимально близко к исходной.

Можно исправить только очевидные технические ошибки, не меняющие смысл.

### 6

Если пользователь объяснил особый смысл:

> бокс — помогает выпустить накопившуюся энергию

сохрани:

```json
{
  "label": "бокс",
  "user_context": "помогает выпустить накопившуюся энергию"
}
```

### 7

Не придумывай `user_context`.

### 8

Опечатки и разговорные формулировки не являются причиной удалить объект.

---

# 6. Формат Parser

```json
{
  "items": [
    {
      "id": "item_1",
      "label": "стейки",
      "area": "food",
      "user_context": null
    },
    {
      "id": "item_2",
      "label": "путешествовать на самолёте или машине",
      "area": "travel",
      "user_context": null
    }
  ]
}
```

---

# 7. КРИТИЧЕСКОЕ ИЗМЕНЕНИЕ BACKEND

После Parser вся дальнейшая система должна работать **с результатом Parser**.

Не валидировать результаты модели против исходного raw-text.

Не делать повторно:

```js
split(/[,;\n]+/)
```

для проверки существования объекта.

Вместо этого:

```text
raw input
→ parser.items
→ analyst
→ critic
→ validate against parser.items
```

Если Analyst возвращает:

`путешествовать на самолёте или машине`

валидатор должен искать этот объект среди `parser.items`.

---

# 8. ANALYST — не объяснять весь список

Добавить правило:

**Не все введённые вещи обязаны участвовать в результате.**

Некоторые элементы могут:

- остаться отдельным предпочтением;
- не поддерживать сильную связь;
- быть outlier;
- пока не иметь достаточного контекста.

Это нормально.

Не нужно искусственно присоединять все объекты к паттернам.

---

# 9. BEST AVAILABLE INSIGHT

Главное правило:

**всегда пытайся вернуть лучший доступный результат.**

Не отвергай весь анализ только потому, что нельзя построить 3–4 одинаково сильных паттерна.

Один отличный вывод лучше:

- трёх слабых;
- или полного отказа.

---

# 10. Количество кандидатов

Не требовать обязательно:

> 8–12 паттернов.

Использовать как ориентир:

**4–10 потенциальных гипотез, если данные позволяют.**

Если сильных гипотез меньше — не создавать лишние.

---

# 11. Главный инсайт

Минимальное требование:

- минимум 3 разных смысловых выбора;
- конкретный повторяющийся механизм;
- отсутствие очевидного пересказа.

Желательно использовать разные области жизни.

Но НЕ требовать три разных технических `area`.

Например:

- бег;
- сноуборд;
- прогулки;
- езда на машине;

могут технически попасть рядом, но описывать разные формы опыта.

Количество UI-категорий — не критерий истинности связи.

---

# 12. Паттерны

Основной паттерн:

- желательно 3+ evidence.

Дополнительный паттерн:

- допустимо 2 сильных evidence, если связь конкретная и действительно интересная.

Результат может содержать:

```text
1–4 patterns
```

Не требовать минимум два.

---

# 13. Unexpected connections

Количество:

```text
0–4
```

Если сильной неожиданной пары нет — вернуть пустой массив.

Не придумывать слабую пару ради заполнения интерфейса.

Разные `area` предпочтительны, но не являются обязательным техническим условием.

---

# 14. CRITIC — новая логика

Critic должен выбирать качество, а не полноту.

Добавить:

> Верни столько связей, сколько удалось подтвердить честно.
>
> Один сильный паттерн лучше нескольких натянутых.
>
> Не требуй, чтобы анализ использовал весь пользовательский список.
>
> Не отклоняй результат только потому, что не удалось получить заранее установленное количество паттернов или пар.

---

# 15. `insufficient_data` — только крайний случай

Возвращать:

```json
{"insufficient_data": true}
```

только если невозможно сформулировать **даже один содержательный главный вывод**, который:

- подтверждается минимум 3 разными пользовательскими выборами;
- содержит конкретный механизм;
- не является банальностью;
- не требует выдумывать свойства объектов.

Не использовать `insufficient_data` из-за того, что:

- есть только один паттерн;
- нет неожиданных пар;
- evidence находится только в двух `area`;
- часть введённых вещей осталась вне анализа.

---

# 16. ОБЯЗАТЕЛЬНЫЕ ИЗМЕНЕНИЯ В BACKEND VALIDATION

Эти изменения необходимо внести именно в код.

Одного изменения prompt недостаточно.

## A. Patterns

Сейчас логика примерно требует:

```js
patterns.length < 2
```

Убрать.

Разрешить:

```js
patterns.length >= 1
patterns.length <= 4
```

---

## B. Unexpected connections

Сейчас требуется минимум 2.

Убрать.

Разрешить:

```js
unexpected_connections.length >= 0
unexpected_connections.length <= 4
```

Пустой массив является валидным результатом.

---

## C. Main evidence areas

Сейчас validator требует:

- минимум 3 evidence;
- минимум 3 разных `area`.

Убрать обязательность трёх `area`.

Требовать:

- минимум 3 разных parsed items.

Пример:

```js
new Set(main_evidence.map(e => e.item_id)).size >= 3
```

Разнообразие `area` можно использовать для scoring, но НЕ для hard validation.

---

## D. Validate against Parser

Это обязательное изменение.

Сейчас validation проверяет название через исходные строки пользователя.

Перестать делать это.

Использовать:

```js
parsedItems
```

как canonical source.

Например:

```js
const knownItems = new Map(
  parsedItems.map(item => [item.id, item])
)
```

Желательно, чтобы evidence возвращал:

```json
{
  "item_id": "item_7",
  "reason": "..."
}
```

а не полагался только на exact string matching.

Это существенно надёжнее.

---

# 17. Рекомендуемая новая схема evidence

Вместо:

```json
{
  "item": "бегать",
  "area": "hobbies",
  "reason": "..."
}
```

использовать:

```json
{
  "item_id": "item_10",
  "item": "бегать",
  "reason": "..."
}
```

`item_id` — источник истины.

`item` — только отображение.

Так модель не сломает validation, если случайно напишет:

`бег`

вместо:

`бегать`.

---

# 18. Regression test

Обязательно добавить тест с этим вводом:

> Айгулька жена и дочь АЙЛИНКА.  
> стейки.  
> сидр.  
> гулять по паркам.  
> ездить на машине!  
> кататься на сноуборде  
> ходить на стадион и смотреть футбол или регби  
> путешествовать, на самолете или машине  
> смотреть видео про космос  
> бегать!  
> ходить на концерты классынх групп типо линкин парк  
> Англия и Армения

Parser должен распознать нормальный набор отдельных смысловых выборов.

Ожидаемый результат API:

```text
HTTP 200
```

а не:

```text
422 insufficient_data
```

При условии, что Analyst действительно нашёл хотя бы один подтверждаемый вывод.

---

# 19. Результат сначала показываем

Не блокировать пользователя требованием:

> Добавьте больше информации.

Сначала показать **best available result**.

Даже если он состоит только из:

- одного главного инсайта;
- одного паттерна;
- без неожиданных пар.

---

# 20. Кнопка «Дополнить вводные»

На экране результата добавить secondary CTA:

**Дополнить вводные**

Она должна быть заметной, но слабее основной навигации результата.

Например:

`[ Дополнить вводные ]`

---

# 21. Что происходит по кнопке

После клика пользователь возвращается к input screen.

ВАЖНО:

весь предыдущий текст остаётся сохранённым.

Ничего не очищать.

Над input показать:

### Хочешь увидеть больше связей?

**Добавь ещё несколько вещей, которые тебе нравятся. Особенно полезны выборы из тех областей, о которых ты ещё не писал.**

---

# 22. Не заставлять отвечать на вопросы

Не показывать обязательную анкету.

Можно дать optional prompts:

**Можно добавить:**

`книги`  
`кино`  
`музыка`  
`еда`  
`места`  
`люди`  
`работа`  
`вещи`  
`хобби`

Только как подсказки.

---

# 23. Повторный анализ

После добавления данных CTA:

**Обновить результат**

Система должна:

1. снова прогнать Parser по полному обновлённому input;
2. провести анализ заново;
3. показать новый результат.

Не анализировать только добавленный fragment отдельно.

---

# 24. Желательно сохранять состояние

Если пользователь:

1. получил результат;
2. нажал «Дополнить вводные»;
3. добавил две вещи;
4. запустил анализ снова;

его предыдущий ввод не должен потеряться даже при ошибке API.

---

# 25. UX после результата

Под финальным результатом:

**Хочешь посмотреть глубже?**

`Дополнить вводные`

Мелким:

**Чем больше разных выборов, тем больше неожиданных связей можно проверить.**

Не говорить:

> Твоих данных недостаточно.

Потому что результат уже получен.

---

# 26. Главное продуктовое правило

Система должна работать так:

```text
маленький, но нормальный ввод
→ хороший компактный результат
```

```text
более богатый ввод
→ более богатый результат
```

А НЕ:

```text
маленький ввод
→ ошибка
```

Главная логика:

**сначала дать ценность → затем предложить углубить.**
